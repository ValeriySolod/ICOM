# Модель аудиту

**Статус:** Чернетка · **Версія:** 0.1 · **Оновлено:** 2026-10-02

`AuditEvent` — повноцінна доменна сутність (AD-08). Вона реалізує перспективу **аудиторського обліку** ([system-context.md §2](../architecture/system-context.md#2-три-перспективи-обліку)).

## 1. AuditEvent

| Атрибут | Опис |
|---|---|
| ID події | Унікальний, незмінний |
| Час запису | Час внесення запису (синхронізоване джерело, з часовим поясом) |
| Дата проведення | Дата господарської операції, якщо вона відрізняється |
| Виконавець (хто) | Користувач. Також роль і межі, у яких діяв, та особа, яка делегувала повноваження (за наявності). |
| Дія | Назва операції, наприклад `approveTransfer`, `completeInventory` |
| Об'єкт | Тип та ID сутності |
| Попереднє значення | Попередні значення змінених атрибутів |
| Нове значення | Нові значення змінених атрибутів |
| Причина | Обов'язкова для виправлень, скасувань, визнання недійсним, дозволів-винятків |
| Пов'язаний документ | ID документа, де застосовно |
| Пов'язана операція | ID господарської операції або справи (передача, кампанія інвентаризації, справа списання) |
| ID кореляції | Об'єднує події однієї транзакції |
| Джерело / контекст сесії | ID сесії, клієнт і мережевий контекст, **якщо це дозволено** політикою та правилами щодо персональних даних |
| Результат | Успіх / відмовлено / помилка (спроби критичних операцій, у яких відмовлено, фіксуються) |
| Дані цілісності | Ланцюжок хешів або рівноцінний засіб виявлення підробки (механізм — OQ-12) |

## 2. Що аудитується

Щонайменше:

- кожна зміна стану основних сутностей: майно, закріплення, розташування, статус, вартість, передача, інвентаризація, списання, обслуговування, документ;
- переходи життєвого циклу документів, погодження та підписи;
- зміни довідників і конфігурації, зокрема процесів, правил розподілу обов'язків і строків зберігання;
- зміни ролей і дозволів;
- доступ до чутливих даних (DC-3/DC-4/DC-5), якщо цього вимагає політика;
- експорт чутливих даних;
- випуск і відкликання міток, а також спроби розпізнати відкликані мітки.

Події безпеки також надходять до потоку журналу безпеки (див. [security-architecture.md §5](../architecture/security-architecture.md#5-аудит-і-журналювання-безпеки)).

## 3. Правила цілісності

- Події аудиту записуються **в тій самій транзакції**, що й зміна (NFR-01).
- Записи лише додаються. Застосунок не має можливості їх змінювати чи видаляти.
- Звичайні адміністратори, включно із системними, не можуть редагувати чи видаляти історію аудиту (BR-25).
- Попередні й нові значення, що містять персональні або чутливі дані, захищаються відповідно до свого класу. Дані аудиту не можуть бути обхідним шляхом повз контроль доступу.
- Зберігання аудиту контролюється й визначається разом із правилами зберігання ([document-retention.md](../compliance/document-retention.md)). Вилучення після завершення строку, якщо воно взагалі дозволене, — контрольована процедура, що фіксується.

## 4. Відкриті питання

- OQ-12 — механізм захисту від підробки: ланцюжок хешів, сховище WORM або зовнішній приймач журналів.
- Строк зберігання записів аудиту та журналів безпеки.
- Які події читання потрібно аудитувати (баланс між контролем і обсягом даних).
